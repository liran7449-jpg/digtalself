# Today 项目架构铁律

> 本规范是 Today（Personal Knowledge Graph / Digital Self）的硬性架构约束。
> 任何代码变更前先通读本文件；与既有代码冲突时，以本规范为准并指出冲突点。

## 1. 分层架构：前端永不直接操作数据库

客户端（Web / iOS / Android / 小程序）一律通过 API → Service → Database 访问数据。

```
React / iOS / Android / 小程序
        ↓
GET /api/v1/today
        ↓
Today Service
        ↓
Database
```

规则：
- 任何前端代码不得直接读写数据库（含 ORM 直查）。
- 新增客户端 = 增加一个调用方，不是重做一个产品。
- 数据访问统一收敛到 API + Service 层。

## 2. 模块之间通过接口交流

禁止跨模块直接读写对方数据。示例：People 需要 Moments 时，只能调用 MomentService。

```
People
   ↓
MomentService
   ↓
Moments
```

MomentService 提供统一出口：`createMoment` / `getMoment` / `updateMoment` / `deleteMoment` / `linkPerson` / `linkPlace` / `linkGoal` / `saveAsMemory`。

规则：
- 每个领域（Moment / Person / Goal / Memory…）有且仅有一个 Service 出口。
- 禁止到处写 `if user.moment.xxx` 式的跨模块硬耦合。
- 模块之间只认接口，不认内部结构；People 需要 Moments 时不得直接碰数据库。

## 3. 数据模型优先设计：不要写死关系

数据库设计优先于 UI——产品本质是 Personal Knowledge Graph，不是页面集合。

- 不要用单值外键写死关系：

```
✗ Moment { person_id, goal_id, place_id }
```

- 用关联表表达多对多关系：

```
Moment
   ├── MomentPerson
   ├── MomentPlace
   ├── MomentGoal
   └── MomentMemory
```

因为一条 Moment 可能同时关联 2 个人、3 个 Goal，甚至同时属于一段旅行、一段关系、一个人生阶段。

## 4. 媒体与元数据分离存储

数据库不存图片 / 视频二进制，只存元数据与存储地址。

```
Database: Media { id, user_id, storage_key, type, width, height, created_at, ... }

Object Storage: /photos/{user_id}/{yyyy}/{MM}/{filename}
```

- 数据库只记录"这张照片在哪里"（storage_key）。
- Web / App / 小程序都从同一个 Object Storage 读取媒体。

## 5. Privacy By Design：拒绝"有 URL 就能看"

数据可能包含私人照片、日记、感情记录、家庭信息、工作信息、生活轨迹、对人的评价、私密想法。从第一天起按隐私优先设计。

- 禁止把资源地址做成永久公开 URL（例如 `https://xxx.com/photo/abc.jpg` 仅凭 URL 即可访问）。
- 访问路径必须是：

```
用户访问 → Backend 校验权限 → 生成可访问的资源地址 → 返回内容
```

- 私密内容仅凭知道 URL 不能访问；分享链接必须走权限判断。

## 6. 一切配置化，禁止 Hard Code

禁止在代码里写死主题、Feature Flag、权限、环境、AI 模型、存储、API URL 等。

```
.env / 配置中心：
DATABASE_URL
STORAGE_URL
AI_API_KEY
APP_ENV
PUBLIC_BASE_URL
```

- 判断条件（如 `theme === "cream"`、`userType === "friend"`）必须来自配置或服务端返回，不得硬编码。
- 密钥永远不能进入前端代码。

## 7. 新功能必须模块化（保证可删除）

新增功能必须自包含，删除成本要低。

```
新增 People →
modules/people/
  PeopleList / PersonDetail / PersonService / PersonRepository / PersonTypes
```

- 禁止"修改很多现有文件顺便加功能"的开发方式。
- 任何新功能都要回答：删除它需要改动多少地方？理想答案是"只删本模块"。
- 反例：删除 Explore → Today / Moments / Me 全挂、数据库迁移失败、AI 挂掉，即耦合过高。

## 8. 前端按领域模块化

禁止把所有组件堆进扁平的 `components/`（Button.tsx / xxx-final-2.tsx 垃圾场）。

```
features/
  today/  moments/  me/  goals/  people/  journey/  memory/  sharing/
```

```
features/moments/
  components/  hooks/  services/  types/  utils/
```

- 新页面 / 新功能先落进对应 feature 目录。
- 各 feature 自包含，组件不跨目录散落。

## 9. Design System 组件化

统一设计系统，禁止各功能自造 UI。

```
Design System：
Typography / Color / Spacing / Button / Input / Modal / Drawer /
Timeline / Moment / Photo / Section / Navigation / Empty State
```

- 新增页面必须复用 Design System 组件。
- 禁止"People 重新设计一套 Button"，防止产品变成 Today 一套 UI、Moments 一套 UI、Me 一套 UI、People 一套 UI、AI 一套 UI。

## 10. API 规范

所有客户端只通过版本化 API 访问服务：

```
GET    /api/v1/today
GET    /api/v1/moments
POST   /api/v1/moments
GET    /api/v1/moments/:id
PATCH  /api/v1/moments/:id
DELETE /api/v1/moments/:id

GET    /api/v1/me
PATCH  /api/v1/me

GET    /api/v1/goals
POST   /api/v1/goals
```

- 必须带 `/v1/` 版本前缀：未来升级到 `/v2/` 时，旧客户端不必强制升级。
- 新端点一律遵循 RESTful 动词 + 资源路径，不得另起风格。

## 11. 数据库必须走 Migration

禁止直接改数据库结构，一切 Schema 变更用迁移脚本：

```
Migration 001  Create users
Migration 002  Create moments
Migration 003  Create media
Migration 004  Add visibility
Migration 005  Add moment_people
```

- 开发 / 测试 / 生产环境的一致性靠 Migration 保证。
- 禁止让 AI 直接"改数据库"。

## 12. 至少三个环境

```
Local（本地开发） / Staging（测试） / Production（正式）
```

- 禁止直接在 Production 里 Vibe Coding，尤其是开始存放真实照片和日记之后。
- 变更先在 Staging 验证，再上 Production。

## 13. 数据可迁移（Export My Data）

用户数据必须可整体导出，不被技术栈锁死：

```
my-digital-life/
  moments/  photos/  people/  goals/  memories/  profile.json
```

- 支持导出 JSON、Markdown、Photos、Videos。
- 这是用户的数字人生，不应被某一个技术栈锁死。

## 14. 稳定 ID（UUID / ULID）

所有核心对象（User / Moment / Person / Goal / Memory / Media）使用稳定 ID，禁止用自增 1、2、3 作为对外标识。

- 统一采用 UUID / ULID 一类稳定 ID。
- 这样 Web、App、小程序、分享链接、API、AI Memory 才能安全引用同一个对象。

## 变更前自检清单（DoD）

任何功能交付前逐项确认：

- [ ] 前端未直接操作数据库，数据全部经 API → Service 获取？
- [ ] 跨模块访问走的是对方 Service 接口，而非直接碰数据？
- [ ] 数据模型变更已写成 Migration，未直接改库？
- [ ] 核心对象使用 UUID / ULID 稳定 ID？
- [ ] 媒体文件走 Object Storage，库中只存 storage_key 与元数据？
- [ ] 私密内容有权限校验，不存在永久公开 URL？
- [ ] 配置进入 .env / 配置系统，无硬编码、无前端密钥？
- [ ] 新功能是自包含模块，删除成本低？
- [ ] 前端组件归入 features/ 并复用 Design System？
- [ ] API 带版本前缀（/v1/）？
- [ ] 变更已在 Staging 验证，未直接改动 Production？
